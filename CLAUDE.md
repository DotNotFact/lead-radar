# Lead Radar

Персональная система поиска заказов и управления действиями для .NET-разработчика
(фриланс + удалённая работа). Работает на личном ПК владельца, единственный пользователь — владелец.

Три задачи в порядке важности:
1. Не пропустить релевантный заказ — уведомление в течение минуты после публикации.
2. Не дать забыть про важное — ежедневная очередь действий с эскалацией просроченного.
3. Накопить данные о рынке для анализа каналов/ниш/ценников через 3–4 недели.

## ЖЁСТКИЕ ИНВАРИАНТЫ

Не обсуждаются и не нарушаются ни при каких оптимизациях.

1. **Никаких автоматических откликов, сообщений и комментариев.** Система только читает и уведомляет.
   Любой исходящий контакт с заказчиком делает человек руками.
2. **Секреты только в `.env`.** `.env`, `*.session`, `*.db` — в `.gitignore` с первого коммита.
   Никогда не логировать значения токенов, ключей, session-строк.
3. **Telegram-аккаунт коллектора — отдельный, не основной.** Только чтение. Не вступать в чаты
   программно, не менять профиль, не отправлять ничего от имени юзербота.
4. **Вежливый парсинг.** Для источников без API: не чаще 1 запроса в 10 секунд на домен, честный
   User-Agent с контактом, уважать `robots.txt`, кэшировать, не долбить при 429/403 — экспоненциальный
   бэкофф и тихий режим на час.
5. **Экспорт всегда обезличен.** Из выгрузки вырезаются user_id, телефоны, email, @username, имена
   собственные. Hard-требование функции экспорта, не опция.
6. **Деградация вместо падения.** Смерть одного источника не роняет систему. Источник помечается
   `degraded`, владелец получает уведомление, остальное работает.
7. **Никаких обходов защиты.** Не обходить капчи, не подделывать сессии, не использовать чужие
   аккаунты, не парсить площадки, где это прямо запрещено и технически заблокировано. Если источник
   не даётся — ручной режим, а не война с ним.

## ТРЕБОВАНИЯ К КОДУ

- Type hints везде, `mypy --strict` проходит.
- Никакой бизнес-логики в обработчиках бота — только вызов сервисов.
- Все внешние вызовы обёрнуты в таймауты и retry с экспоненциальным бэкоффом.
- Структурное логирование в файл с ротацией, отдельный уровень/событие для «источник сломался».
- Конфигурация — только через `.env` и YAML, никаких констант в коде.
- Каждая фаза заканчивается рабочим состоянием: система не должна быть сломана между фазами.
- Комментарии и коммиты — на русском.

## СТЕК

Python 3.13 (в промте указан 3.12, на машине владельца установлен только 3.13 — используем его,
совместимость со всем стеком ниже сохраняется), Telethon, aiogram 3.x, httpx + selectolax,
feedparser, SQLite + aiosqlite, APScheduler, pydantic-settings, pytest + pytest-asyncio.

## ТЕКУЩЕЕ СОСТОЯНИЕ ПРОЕКТА

- **Фаза 0 (фундамент) — выполнена.** Структура проекта, конфиги (`sources.yaml`, `keywords.yaml`,
  `actions.yaml`), `.env.example`, миграции БД, модели, слой БД, структурное логирование, тесты.
- **Фаза 1 (hh.ru) — выполнена.** `src/collectors/hh_ru.py` (пагинация, дедуп по id, полное
  описание вакансии вторым запросом), `src/scoring/{budget.py,scorer.py,dedup.py}`,
  `src/core/{yaml_config.py,repository.py,http.py}` (общий ретрай с бэкоффом на 429/5xx),
  `scripts/collect_hh.py` для разового прогона. 30 тестов, `mypy --strict` чист.
  **Важно:** `api.hh.ru` отдаёт 403 (DDoS-Guard) с IP песочницы разработки — обычный интернет
  при этом работает (проверено на example.com и hh.ru/robots.txt). Живой гейт "100+ реальных
  вакансий в БД" не пройден из песочницы принципиально (обходить защиту — нарушение инварианта 7).
  Заменён интеграционным тестом (`tests/test_collect_hh_pipeline.py`), гоняющим тот же объём и
  форму данных через весь конвейер на моках. **Владельцу нужно один раз запустить
  `python -m scripts.collect_hh` на своей машине**, чтобы наполнить БД реальными вакансиями —
  оттуда `api.hh.ru`, скорее всего, ответит нормально.
- **Фаза 2 (Telegram + бот + уведомления) — выполнена (код и тесты; живая проверка не сделана,
  см. ниже).** `src/collectors/telegram.py` (Telethon-клиент внедряется снаружи через Protocol —
  тестируется без реальной сессии; catch-up через `fetch()`, реалтайм через
  `register_realtime_handler()`), `src/notifier/{formatter.py,keyboard.py,notifier.py}`
  (формат сообщения из ТЗ, инлайн-кнопки Открыть/Ответил/Мимо), `src/control/bot.py`
  (aiogram-роутер: `/health`, `/sources`, `/pause`, `/resume`, `/addchat`, обработчик кнопок
  исхода лида), `src/control/chat_config.py` (чаты из /addchat хранятся отдельно от
  sources.yaml, чтобы не терять комментарии владельца при перезаписи), миграция
  `0002_system_state.sql`. 46 тестов, `mypy --strict` чист.
  **Не проверено вживую и не может быть проверено из песочницы:**
  - `api.telegram.org` не резолвится/не коннектится из этой машины (сетевая ошибка, не 403) —
    даже `getMe` с реальным токеном бота не прошёл. Обычный интернет при этом работает
    (см. Фазу 1). Значит live-тест бота и Telethon-сессии возможен только на машине владельца.
  - Живая сессия Telethon требует интерактивного ввода кода из СМС на настоящий телефон —
    в принципе не может быть создана автоматически, только владельцем руками.
  - Ни одно сообщение не было отправлено ни в какой чат/канал за время работы — отправка
    сообщений требует явного разрешения владельца в чате и реального `CHANNEL_ID`, которого
    нет.
  **Что нужно от владельца, чтобы включить эту фазу живьём:**
  1. `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` с my.telegram.org (для отдельной симки) → в `.env`.
  2. Первый запуск Telethon-клиента на своей машине (один раз ввести код из Telegram) —
     появится `*.session` файл, он в `.gitignore`.
  3. Создать приватный канал, добавить туда бота-администратором, вписать `CHANNEL_ID` в `.env`.
  4. Заполнить `config/sources.yaml` → `telegram.chats` (60–100 чатов) и поставить
     `enabled: true`.
  Полная связка (планировщик + Telethon realtime + polling бота) будет собрана в `src/main.py`
  в Фазе 3 вместе с APScheduler для ежедневного брифа — тогда же будет что реально запускать
  одной командой.
- **Фаза 3 (модуль действий, бриф, планировщик) — выполнена.** `src/actions/materializer.py`
  (превращает шаблоны `actions.yaml` в строки `actions` идемпотентно: daily/every_3_days/weekly,
  сезонные по `MM-DD` раз в год, разовые — один раз навсегда), `src/actions/brief.py` (дайджест:

  `src/control/bot.py`. **`src/main.py`** — единая точка входа: APScheduler крутит опрос hh.ru
  по расписанию, отправку уведомлений (раз в минуту), ежедневный бриф (cron по
  `DAILY_BRIEF_TIME`); Telegram catch-up + realtime поднимаются, если заполнены
  `TELEGRAM_API_ID/HASH`; polling бота. Отсутствие `CHANNEL_ID` не роняет процесс — просто не
  шлёт уведомления/бриф (инвариант 6). 63 теста, `mypy --strict` чист.

### Что заполнено в `.env`
- `BOT_TOKEN` — заполнен.
- `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` — нужно получить на my.telegram.org для отдельной симки.
- `CHANNEL_ID` — нужно создать приватный канал и вписать id.
- Список Telegram-чатов в `config/sources.yaml` — нужно собрать 60–100 штук (см. комментарий в файле).
- Порог скоринга, минимальный бюджет, время брифа — стоят дефолты, требуют ручной настройки владельцем.

Работай фазами. После каждой фазы — остановиться и показать результат, ждать явной команды на
продолжение.
